# Git·GitHub 개발 규칙

이 문서는 프로젝트의 브랜치·커밋·PR·출시·개발 기록 관리 규칙을 정리한다.

관련 작업: [docs: Git·GitHub 개발 규칙 정리 및 문서화 (#1)](https://github.com/yong203/aiTrade/issues/1)

## 1. 저장소 구성

- 프론트엔드, 백엔드, 매매·분석 워커, DB 마이그레이션, 배포 설정과 문서를 하나의 모노레포에서 관리한다.
- Git은 프로젝트 루트의 `.git` 하나로 관리한다.
- 프론트엔드와 백엔드는 폴더로 구분한다. 각 서비스의 실행 컨테이너는 분리할 수 있다.
- API 키, 계좌별 비밀 설정, 실제 DB 데이터, 원시 수집 데이터, 로그, 학습 모델 산출물은 Git에 저장하지 않는다.

## 2. 이슈 작성과 메타데이터

이슈 제목은 작업 PR과 동일한 작업 유형·영역 표기 규칙을 적용한다. 이슈 자신의 번호는 제목에 중복 작성하지 않는다.

- 프론트엔드 작업에는 `[FE]`, 백엔드 작업에는 `[BE]`, 두 영역을 함께 변경하는 작업에는 `[FE/BE]`를 표시한다.
- 문서·CI 등 영역 구분이 필요 없는 작업에서는 영역 표시를 생략한다.

제목 형식:

```text
유형: 작업 설명
유형: [FE] 작업 설명
유형: [BE] 작업 설명
유형: [FE/BE] 작업 설명
```

예시:

```text
feat: [FE] 거래내역 대시보드 구현
feat: [BE] 거래내역 조회 API 구현
feat: [FE/BE] 거래내역 조회 기능 구현
docs: Git·GitHub 개발 규칙 정리 및 문서화
```

현재 저장소의 작업 유형 라벨:

| 작업 | 라벨 |
|---|---|
| 기능 구현 | `✨ Feature` |
| 버그 수정 | `🚨 Fix` |
| 문서 | `📝 Docs` |
| 테스트 | `🧪 Test` |
| 코드 구조 개선 | `♻️ Refactor` |
| 기타 관리 | `🔧 Chore` |
| CI 설정 변경 | `⚙️ CI` |
| 출시·배포 | `🔖 Release` |

## 3. 이슈·브랜치·PR 연결

이슈 생성 → 연결된 작업 브랜치 생성 → `dev` 대상 PR 생성 → 병합 후 이슈 종료 순서로 진행한다.

- 브랜치 이름에 이슈 번호를 넣고 일반 Git 명령으로 생성·push하는 것만으로는 GitHub Development 연결이 등록되지 않는다.
- 새 작업 브랜치는 이슈의 Create a branch 또는 GitHub CLI의 이슈 브랜치 생성 기능으로 연결한다. 기준 브랜치는 `dev`로 지정한다.
- 저장소의 기본 브랜치는 `dev`다. 이슈를 완료하는 작업 PR에는 `Closes #42`처럼 종료 키워드를 작성한다. 해당 PR을 `dev`에 병합하면 연결된 이슈가 자동 종료된다.

브랜치 생성 예시:

```bash
gh issue develop 42 --repo yong203/aiTrade --base dev --name feat/42-fe-account-history --checkout
```

## 4. 브랜치 전략

`release/*`를 생략한 Git flow 변형을 사용한다.

기본 브랜치와 통합 브랜치 이름은 `dev`로 통일한다. 별도 프론트·백엔드 통합 브랜치는 두지 않는다. 일반 작업은 최신 `dev`에서 브랜치를 생성한다. Git 브랜치는 담당 폴더만이 아니라 저장소 전체 상태를 가진다.

| 브랜치 | 역할 | 유지 |
|---|---|---|
| `main` | 검증한 출시 버전 관리 | 상시 |
| `dev` | 완료한 기능·수정 통합 및 검증 | 상시 |
| `feat/*` | 새로운 기능 구현 | 작업 완료 후 삭제 |
| `fix/*` | 버그 수정 | 작업 완료 후 삭제 |
| `docs/*` | 문서 변경 | 작업 완료 후 삭제 |
| `test/*` | 테스트 변경 | 작업 완료 후 삭제 |
| `refactor/*` | 기능을 유지하는 코드 구조 개선 | 작업 완료 후 삭제 |
| `chore/*` | 기타 관리 작업 | 작업 완료 후 삭제 |
| `ci/*` | CI 설정 변경 | 작업 완료 후 삭제 |
| `release/*` | 현재 사용하지 않음 | 필요성이 확인되면 도입 검토 |

## 5. 작업 브랜치 이름

작업 브랜치 유형은 `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`를 사용한다. `init`은 최초 초기화 커밋에만 사용한다.

- 브랜치에서는 소문자 `fe`, `be`를 사용한다.
- 브랜치의 이슈 번호에는 `#`를 붙이지 않는다.
- 작업 설명은 소문자 영문과 하이픈으로 작성한다.
- FE·BE를 함께 구현하는 작업은 `feat/42-account-history`처럼 영역 표시를 생략할 수 있다.
- 작업 브랜치는 병합 후 삭제한다. 후속 수정은 최신 `dev`에서 새 브랜치를 생성한다.

기본 형식:

```text
유형/이슈번호-작업설명
```

영역별로 나누는 작업의 형식:

```text
유형/이슈번호-fe-작업설명
유형/이슈번호-be-작업설명
```

예시:

```text
feat/42-fe-account-history
feat/42-be-account-history
fix/43-be-partial-fill-balance
docs/44-github-workflow
chore/46-ci-checks
```

## 6. 커밋 형식

Conventional Commits를 사용하며 범위(scope)는 생략한다.

- 작업 브랜치의 개별 커밋에서는 이슈 번호를 생략한다.
- 최초 초기화 커밋은 `init: aiTrade 프로젝트 초기화`로 작성하고, 사용자 확인을 받은 간단한 README만 포함한다.
- FE·BE 작업의 커밋에서는 해당 영역을 표시한다. 영역 구분이 필요 없는 문서·관리 작업은 생략한다.
- 커밋 유형은 브랜치 유형이 아니라 실제 변경 내용에 따라 선택한다.
- 괄호로 범위를 지정하는 `feat(account):` 형식은 사용하지 않는다.

기본 형식:

```text
유형: 변경 설명
유형: [FE] 변경 설명
유형: [BE] 변경 설명
유형: [FE/BE] 변경 설명
```

예시:

```text
feat: [BE] 거래내역 조회 API 구현
feat: [FE] 거래내역 테이블 추가
fix: [BE] 거래내역 날짜 정렬 수정
test: [BE] 거래내역 페이지네이션 검증
docs: GitHub 개발 규칙 정리
```

| 유형 | 사용 |
|---|---|
| `init` | 저장소 최초 초기화 커밋 |
| `release` | 검증한 버전 출시 |
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 변경 |
| `test` | 테스트 변경 |
| `refactor` | 기능을 유지하는 코드 구조 개선 |
| `chore` | 기타 관리 작업 |
| `ci` | CI 설정 변경 |

## 7. 작업 PR

프론트엔드 작업 PR에는 `[FE]`, 백엔드 작업 PR에는 `[BE]`, FE·BE를 함께 변경하는 PR에는 `[FE/BE]`를 사용한다. 문서·CI 등 영역 구분이 필요 없는 PR에서는 표시를 생략한다. 하나의 PR은 하나의 논리적 작업으로 정리한다.

- PR 생성 시 이 문서의 작업 유형 라벨 표에 따라 변경 내용에 맞는 라벨을 지정한다. 출시 PR에는 `🔖 Release` 라벨을 지정한다.

제목 형식:

```text
유형: 작업 설명 (#이슈번호)
유형: [FE] 작업 설명 (#이슈번호)
유형: [BE] 작업 설명 (#이슈번호)
유형: [FE/BE] 작업 설명 (#이슈번호)
```

예시:

```text
feat: [FE] 거래내역 대시보드 구현 (#42)
feat: [BE] 거래내역 조회 API 구현 (#42)
fix: [BE] 부분체결 후 잔고 계산 수정 (#43)
docs: GitHub 개발 규칙 정리 (#44)
```

## 8. 머지 규칙

- `dev`의 스쿼시 커밋 메시지는 작업 PR 제목과 동일하게 작성한다.
- 출시 PR 제목과 `main`의 스쿼시 커밋 메시지는 `release: v0.1.0 출시`처럼 작성한다.
- 출시 후 `main`을 `dev`에 반영할 때는 스쿼시하지 않는다. 다음 출시 PR의 커밋 비교와 병합 기준을 연결하기 위한 절차다.
- `main`에는 초기 README 커밋을 제외하면 출시 단위 변경 기록을 남긴다.
- 출시 준비와 다음 기능 개발을 동시에 진행해야 할 때 `release/*` 도입을 검토한다.

| 방향 | 방식 | 결과 |
|---|---|---|
| 작업 브랜치 → `dev` | Squash merge | 작업 단위 커밋 하나 |
| `dev` → `main` | Squash merge | 출시 단위 커밋 하나 |
| 출시 후 `main` → `dev` | 일반 Merge | 출시 이력 및 커밋 관계 동기화 |

전체 흐름:

```text
이슈 생성
  → 최신 dev에서 작업 브랜치 생성
  → 개발·커밋
  → PR·리뷰·검증
  → dev에 Squash merge
  → 작업 브랜치 삭제

출시할 변경 검증
  → dev에서 main으로 출시 PR
  → main에 Squash merge
  → 병합한 커밋의 테스트·Docker 이미지 빌드
  → 버전 태그 생성
  → main을 dev에 일반 Merge
  → 맥북의 Docker 컨테이너에 해당 버전 자동 배포
  → 주문·체결·잔고 대조 후 매매 재개
```

## 9. 출시와 실거래 배포

- 검증한 출시 변경을 `main`에 병합하면 자동 배포하며, 주문 상태 확인과 매매 재개 절차를 거친다.
- 배포는 병합한 커밋의 테스트와 Docker 이미지 빌드가 성공한 경우에 진행한다. 맥북이 꺼져 있거나 연결이 끊겼으면 배포를 대기시키며, 연결 복구 후 주문 상태를 확인하고 진행한다.
- 검증한 `main` 커밋에 버전 태그를 생성한다. 출시한 태그를 다른 커밋으로 옮기지 않는다.
- GitHub Release에 주요 변경, 포함한 이슈, 출시 검증 결과와 주의사항을 기록한다.
- 실제 배포 기록에는 코드 커밋·태그, Docker 이미지 digest, 모델·전략·위험 설정 버전과 배포 결과를 남긴다.
- 실거래 Docker는 검증한 이미지와 설정을 고정하고 개발 폴더나 `latest` 이미지를 자동으로 따라가지 않는다.
- 배포 전 신규 자동 주문을 중지하고 진행 중인 주문 상태를 저장·확인한다. 컨테이너 업데이트 후 증권사 주문·체결·잔고를 대조하고 정상 확인 후 매매를 재개한다. 배포 또는 대조에 실패하면 매매 재개를 보류한다.
- 이전 버전을 보관한다. 프로그램 롤백은 이미 체결된 거래를 되돌리지 않으며 데이터베이스 호환성도 확인해야 한다.
