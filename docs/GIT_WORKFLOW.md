# Git·GitHub 개발 규칙

이 문서는 프로젝트의 브랜치·커밋·PR·출시·개발 기록 관리 규칙을 정리한다.

관련 작업: [docs: Git·GitHub 개발 규칙 정리 및 문서화 (#1)](https://github.com/yong203/aiTrade/issues/1)

## 1. 저장소 구성

- 프론트엔드, 백엔드, 매매·분석 워커, DB 마이그레이션, 배포 설정과 문서를 하나의 모노레포에서 관리한다.
- Git은 프로젝트 루트의 `.git` 하나로 관리한다.
- 프론트엔드와 백엔드는 폴더로 구분한다. 각 서비스의 실행 컨테이너는 분리할 수 있다.
- API 키, 계좌별 비밀 설정, 실제 DB 데이터, 원시 수집 데이터, 로그, 학습 모델 산출물은 Git에 저장하지 않는다.

## 2. 이슈 작성과 메타데이터

### 이슈·PR 공통 작성 원칙

이슈·PR은 대화를 모르는 독자도 작업 내용과 결과를 정확히 파악할 수 있게 작성한다.

- 이슈에는 이번에 할 작업과 기대 결과를 쓴다.
- PR에는 실제 변경한 내용과 확인한 결과를 쓴다.
- 작업 항목에는 구체적인 대상과 수행 내용을 명시한다.
- 조건·범위·상태에 따라 작업이나 결과의 의미가 달라지면 해당 조건·범위·상태를 명시한다.
- 작업 판단에 도움이 없으면 배경 설명·반복 문구·대화 이력·작업 과정 나열을 생략한다.

### 작업 범위 확인

이슈 생성 요청을 받으면 초안 작성 전에 다음 항목을 파악한다.

- 목적: 해결할 문제 또는 얻으려는 결과
- 작업 대상: 이번에 다룰 기능·화면·문서·규칙
- 수행 내용: 이번 이슈에서 할 구체적인 작업
- 완료 기준: 작업이 끝났음을 확인할 결과와 방법

진행 순서:

1. 기존 대화와 관련 문서에서 확인한 내용을 짧게 요약해 사용자에게 보여준다.
2. 범위·기대 결과·완료 기준이 모호하면 가능한 해석이나 선택지를 제시해 질문한다.
3. 확인한 목적·작업 대상·수행 내용·완료 기준으로 제목·본문 전체 초안을 작성한다.
4. 전체 초안에 대한 별도 명시적 승인을 받은 뒤 이슈를 생성한다.

- 요청이 명확하면 작업 요약과 전체 초안을 함께 제시한다.
- 이미 사용자가 지정하거나 확인한 내용은 반복해서 질문하지 않는다.
- 작은 작성 세부사항은 기존 규칙에 따라 정한다.
- 이미 승인된 동일 초안은 다시 승인받지 않는다.

### 이슈 본문 작성

- 목적에는 해결할 문제와 기대 결과를 짧게 쓴다.
- 작업 범위에는 사용자와 정한 이번 작업을 항목별로 쓴다.
- 완료 조건은 확인 가능한 결과와 확인 방법을 체크리스트로 쓴다.
- 조사·설계 작업이면 확인할 질문과 남길 결과물 또는 결정할 사항을 구체적으로 쓴다.
- 작업 범위를 넓히려면 사용자와 논의해 정한다.

### 제목·라벨

이슈 제목은 아래 작업 유형·영역 표기 규칙을 따른다. 이슈 자신의 번호는 제목에 중복 작성하지 않는다.

- [작업 요청 템플릿](../.github/ISSUE_TEMPLATE/task.md)에 목적·작업 범위·완료 조건을 작성한다.
- 라벨은 아래 작업 유형 표에 따라 선택한다.

작업별 제목 표기:

| 작업 | 유형·영역 표기 |
|---|---|
| 프론트엔드 구현 | 작업 유형과 `[FE]` |
| 백엔드 구현 | 작업 유형과 `[BE]` |
| 프론트엔드·백엔드 함께 변경 | 작업 유형과 `[FE/BE]` |
| 제품 UI/UX·프로토타입 설계 | `design`, 영역 표시 생략 |
| 디자인의 실제 프론트엔드 구현 | `feat: [FE]`, 설계 작업과 별도 관리 |
| 문서·CI 등 영역 구분이 필요 없는 작업 | 작업 유형만 표시 |

제목 형식:

```text
유형: 작업 설명
유형: [FE] 작업 설명
유형: [BE] 작업 설명
유형: [FE/BE] 작업 설명
```

예시:

```text
feat: [FE] 거래내역 대시보드 구현
feat: [BE] 거래내역 조회 API 구현
feat: [FE/BE] 거래내역 조회 기능 구현
design: 전체 UI/UX 고해상도 프로토타입 설계
docs: Git·GitHub 개발 규칙 정리 및 문서화
```

현재 저장소의 작업 유형 라벨:

| 작업 | 라벨 |
|---|---|
| 기능 구현 | `✨ Feature` |
| 버그 수정 | `🚨 Fix` |
| 제품 UI/UX·프로토타입 설계 | `🎨 Design` |
| 문서 | `📝 Docs` |
| 테스트 | `🧪 Test` |
| 코드 구조 개선 | `♻️ Refactor` |
| 기타 관리 | `🔧 Chore` |
| CI 설정 변경 | `⚙️ CI` |
| 출시·배포 | `🔖 Release` |

## 3. 이슈·브랜치·PR 연결

이슈 생성 → 연결된 작업 브랜치 생성 → `dev` 대상 PR 생성 → 병합 후 이슈 종료 순서로 진행한다.

- 새 작업 브랜치는 최신 `dev`를 기준으로 생성한다.
- GitHub Development 연결은 이슈의 Create a branch 또는 GitHub CLI의 이슈 브랜치 생성 기능으로 등록한다.
- 이슈를 완료하는 작업 PR에는 `Closes #42`처럼 종료 키워드를 작성한다.
- 종료 키워드를 포함한 작업 PR을 기본 브랜치인 `dev`에 병합하면 해당 이슈가 자동 종료된다.

브랜치 생성 예시:

```bash
gh issue develop 42 --repo yong203/aiTrade --base dev --name feat/42-fe-account-history --checkout
```

## 4. 브랜치 전략

`dev`에서 작업을 통합하고 `main`에서 출시 버전을 관리하는 Git flow 변형을 사용한다.

- 프론트·백엔드의 기본·통합 브랜치는 공통 `dev`를 사용한다.
- 일반 작업은 최신 `dev`에서 브랜치를 생성한다.
- Git 브랜치는 저장소 전체 상태를 가진다.

| 브랜치 | 역할 | 유지 |
|---|---|---|
| `main` | 검증한 출시 버전 관리 | 상시 |
| `dev` | 완료한 기능·수정 통합 및 검증 | 상시 |
| `feat/*` | 새로운 기능 구현 | 작업 완료 후 삭제 |
| `fix/*` | 버그 수정 | 작업 완료 후 삭제 |
| `design/*` | 제품 UI/UX·프로토타입 설계 | 작업 완료 후 삭제 |
| `docs/*` | 문서 변경 | 작업 완료 후 삭제 |
| `test/*` | 테스트 변경 | 작업 완료 후 삭제 |
| `refactor/*` | 기능을 유지하는 코드 구조 개선 | 작업 완료 후 삭제 |
| `chore/*` | 기타 관리 작업 | 작업 완료 후 삭제 |
| `ci/*` | CI 설정 변경 | 작업 완료 후 삭제 |
| `release/*` | 현재 사용하지 않음 | 필요성이 확인되면 도입 검토 |

## 5. 작업 브랜치 이름

작업 브랜치 유형은 `feat`, `fix`, `design`, `docs`, `test`, `refactor`, `chore`, `ci`를 사용한다. `init`은 최초 초기화 커밋에만 사용한다.

- 브랜치에서는 소문자 `fe`, `be`를 사용한다.
- 브랜치의 이슈 번호에는 `#`를 붙이지 않는다.
- 작업 설명은 소문자 영문과 하이픈으로 작성한다.
- FE·BE를 함께 구현하는 작업은 `feat/42-account-history`처럼 영역 표시를 생략할 수 있다.
- 디자인 작업은 `design/47-ui-ux-prototype`처럼 영역 표시를 생략한다.
- 작업 브랜치가 병합되면 해당 브랜치를 삭제한다.
- 후속 수정이 필요하면 최신 `dev`에서 새 브랜치를 생성한다.

기본 형식:

```text
유형/이슈번호-작업설명
```

영역별로 나누는 작업의 형식:

```text
유형/이슈번호-fe-작업설명
유형/이슈번호-be-작업설명
```

예시:

```text
feat/42-fe-account-history
feat/42-be-account-history
fix/43-be-partial-fill-balance
design/47-ui-ux-prototype
docs/44-github-workflow
chore/46-ci-checks
```

## 6. 커밋 형식

Conventional Commits를 사용하며 범위(scope)는 생략한다.

- 작업 브랜치의 개별 커밋에서는 이슈 번호를 생략한다.
- 최초 초기화 커밋은 `init: aiTrade 프로젝트 초기화`로 작성한다.
- 최초 초기화 커밋에는 사용자 확인을 받은 간단한 README만 포함한다.
- FE·BE 작업의 커밋에서는 해당 영역을 표시한다.
- 문서·관리 등 영역 구분이 필요 없는 작업의 커밋에서는 영역 표시를 생략한다.
- 디자인 작업의 커밋에는 `design:` 유형을 사용하고 영역 표시를 생략한다.
- 디자인의 실제 프론트엔드 구현 커밋에는 `feat: [FE]`를 사용한다.
- 커밋 유형은 실제 변경 내용에 따라 선택한다.

기본 형식:

```text
유형: 변경 설명
유형: [FE] 변경 설명
유형: [BE] 변경 설명
유형: [FE/BE] 변경 설명
```

예시:

```text
feat: [BE] 거래내역 조회 API 구현
feat: [FE] 거래내역 테이블 추가
fix: [BE] 거래내역 날짜 정렬 수정
design: 전체 UI/UX 고해상도 프로토타입 설계
test: [BE] 거래내역 페이지네이션 검증
docs: GitHub 개발 규칙 정리
```

| 유형 | 사용 |
|---|---|
| `init` | 저장소 최초 초기화 커밋 |
| `release` | 검증한 버전 출시 |
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `design` | 제품 UI/UX·프로토타입 설계 |
| `docs` | 문서 변경 |
| `test` | 테스트 변경 |
| `refactor` | 기능을 유지하는 코드 구조 개선 |
| `chore` | 기타 관리 작업 |
| `ci` | CI 설정 변경 |

## 7. 작업 PR

- 본문은 2절의 이슈·PR 공통 작성 원칙을 따른다.
- 작업 PR의 제목 유형·영역 표기는 2절의 작업별 제목 표를 따른다.
- 하나의 PR은 하나의 논리적 작업으로 정리한다.
- 최종 diff·관련 문서·검증 결과를 근거로 실제 변경 내용과 변경 후 동작 또는 결과를 쓴다.
- 실제 확인한 결과와 미검증 상태를 구분한다.
- 검증 결과는 변경 내용에 맞춰 리뷰 판단에 필요한 확인 방법과 결과만 간결하게 쓴다.
- 검사 항목·파일 수·링크 수는 리뷰 판단에 필요한 경우에만 쓴다.
- 검증하지 않은 항목이 변경의 정확성·적용 판단에 영향을 주면 해당 항목과 이유를 쓴다.
- 실행 동작에 영향이 없는 문서 표현·작성 규칙 변경이면 실행 테스트 미수행 설명을 생략할 수 있다.
- 작업 범위가 바뀌면 제목·본문을 최종 변경 내용에 맞춘다.

- [PR 템플릿](../.github/pull_request_template.md)에 변경 내용·관련 이슈·검증 결과를 작성한다.
- 리뷰에 필요한 참고 사항이 있으면 해당 항목을 작성한다.
- PR 생성 시에는 2절의 작업 유형 라벨 표에 따라 라벨을 지정한다.
- 출시 PR에는 `🔖 Release` 라벨을 지정한다.

제목 형식:

```text
유형: 작업 설명 (#이슈번호)
유형: [FE] 작업 설명 (#이슈번호)
유형: [BE] 작업 설명 (#이슈번호)
유형: [FE/BE] 작업 설명 (#이슈번호)
```

예시:

```text
feat: [FE] 거래내역 대시보드 구현 (#42)
feat: [BE] 거래내역 조회 API 구현 (#42)
fix: [BE] 부분체결 후 잔고 계산 수정 (#43)
design: 전체 UI/UX 고해상도 프로토타입 설계 (#47)
docs: GitHub 개발 규칙 정리 (#44)
```

## 8. 머지 규칙

- `dev`의 스쿼시 커밋 메시지는 작업 PR 제목과 동일하게 작성한다.
- 출시 PR 제목과 `main`의 스쿼시 커밋 메시지는 `release: v0.1.0 출시`처럼 작성한다.
- 출시 후 `main`을 `dev`에 반영할 때는 일반 Merge를 사용한다. 다음 출시 PR의 커밋 비교와 병합 기준을 연결하기 위한 절차다.
- `main`에는 초기 README 커밋을 제외하면 출시 단위 변경 기록을 남긴다.
- 출시 준비와 다음 기능 개발을 동시에 진행해야 할 때 `release/*` 도입을 검토한다.

| 방향 | 방식 | 결과 |
|---|---|---|
| 작업 브랜치 → `dev` | Squash merge | 작업 단위 커밋 하나 |
| `dev` → `main` | Squash merge | 출시 단위 커밋 하나 |
| 출시 후 `main` → `dev` | 일반 Merge | 출시 이력 및 커밋 관계 동기화 |

전체 흐름:

```text
이슈 생성
  → 최신 dev에서 작업 브랜치 생성
  → 개발·커밋
  → PR·리뷰·검증
  → dev에 Squash merge
  → 작업 브랜치 삭제

출시할 변경 검증
  → dev에서 main으로 출시 PR
  → main에 Squash merge
  → 병합한 커밋의 테스트·Docker 이미지 빌드
  → 버전 태그 생성
  → main을 dev에 일반 Merge
  → 맥북의 Docker 컨테이너에 해당 버전 자동 배포
  → 주문·체결·잔고 대조 후 매매 재개
```

## 9. 출시와 실거래 배포

- 검증한 출시 변경을 `main`에 병합하면 자동 배포 절차를 시작한다.
- 병합한 커밋의 테스트와 Docker 이미지 빌드가 성공한 경우에만 배포한다.
- 맥북이 꺼져 있거나 연결이 끊기면 배포를 대기시킨다.
- 연결이 복구되면 주문 상태를 확인한 뒤 배포한다.
- 검증한 `main` 커밋에 버전 태그를 생성한다.
- 출시한 태그는 원래 커밋에 고정한다.
- GitHub Release에 주요 변경, 포함한 이슈, 출시 검증 결과와 주의사항을 기록한다.
- 실제 배포 기록에는 코드 커밋·태그, Docker 이미지 digest, 모델·전략·위험 설정 버전과 배포 결과를 남긴다.
- 실거래 Docker는 검증한 이미지와 설정을 고정한다.
- 실거래 Docker가 개발 폴더나 `latest` 이미지를 자동으로 따라가지 않게 한다.
- 배포 전에는 신규 자동 주문을 중지한다.
- 배포 전에는 진행 중인 주문 상태를 저장·확인한다.
- 컨테이너 업데이트 후에는 증권사 주문·체결·잔고를 대조한다.
- 배포와 대조가 정상이면 매매를 재개한다.
- 배포 또는 대조에 실패하면 매매 재개를 보류한다.
- 이전 버전을 보관한다.
- 프로그램을 롤백할 때는 데이터베이스 호환성을 확인한다.
- 프로그램 롤백은 이미 체결된 거래를 되돌리지 않는다.
