# 성장과 개선 기록

기능에서 발견한 문제, 해결·개선 과정, 수치 변화와 최종 결과를 기록한다. 실제 사례가 생길 때 아래 양식으로 추가한다.

## 기록 양식

```markdown
## 날짜 — 기능과 개선 제목

관련 이슈/PR:

### 문제
어떤 상황에서 어떤 문제가 있었고, 사용자에게 어떤 영향을 주었는가?

### 원인과 해결
원인은 무엇이며, 어떤 부분을 어떻게 수정했는가? 그 방법을 선택한 이유는?

### 개선 전후 수치
측정 조건과 방법:

| 지표 | 개선 전 | 개선 후 | 변화 |
|---|---|---|---|
| | | | |

### 최종 결과
무엇이 해결되었고 무엇이 남았는가? 부작용이나 결과의 한계는?
```

수치는 같은 조건에서 비교하고, 측정하지 않은 항목은 ‘미측정’으로 적는다.

## 나중에 검토할 거리

### 주문 제출 방식

현재 선택은 **AI별 순서 처리 + 서로 다른 AI 간 병렬 제출**이며, 아직 미구현·미측정이다. 아래 순서는 제출과 접수 결과 처리 기준이며, 체결 상태는 주문별로 별도 확인한다.

| 방식 | 동작 | 장점 | 단점 |
|---|---|---|---|
| 전체 순서 처리 | 모든 AI의 주문을 한 건씩 제출하고, 접수 결과를 처리한 뒤 다음 주문을 제출한다. | 구현과 문제 추적이 간단하고, 제출 순서를 관리하기 쉽다. | 앞선 요청이 느리면 다른 AI의 주문도 대기한다. |
| **AI별 순서 처리 + 병렬 제출 (현재 선택)** | 같은 AI의 주문은 순서대로 제출하고, 서로 다른 AI의 주문은 동시에 제출할 수 있다. | AI별 제출 순서를 유지하면서 다른 AI 때문에 생기는 대기를 줄일 수 있다. | 공용 계좌의 현금·수량 예약과 전체 동시 제출 수를 함께 관리해야 한다. |
| 제한된 전체 병렬 처리 | AI 구분 없이 정해진 동시 제출 수까지 주문을 제출한다. 같은 AI의 주문도 병렬로 제출할 수 있다. | 주문이 많을 때 제출 대기를 줄일 수 있다. | 같은 AI의 주문 순서와 자금·수량 충돌, 중지·취소·장애 처리가 복잡해진다. |

투자자 수·주문량이 늘면 같은 조건에서 **제출 대기시간·접수 응답시간·오류율**을 비교해 현재 방식을 유지할지 개선할지 판단한다.

### AI 운영을 유지한 수동 매도

- **현재 설계:** 해당 AI를 중지하고 미체결 자동 주문의 취소·종료를 확인한 뒤 수동 매도한다.
- **후속 검토:** AI를 중지하지 않고 해당 AI의 보유종목을 수동 매도할 수 있게 하는 방식이다. 아직 채택·구현하지 않았다.
- **검토할 점:** 같은 종목의 자동 주문과 수량 중복 사용 방지, 기존 미체결 주문 처리, 수동 매도 결과의 AI 판단 반영과 직후 재매수 여부를 정해야 한다. 적용을 검토할 때 수동 매도까지의 대기시간·자동매매 중단시간·주문 충돌 및 거절 건수를 비교한다.

### 실계좌 입출금 자동 인식

- **현재 범위:** 실계좌 입금 후 서버가 실행 중인 상태에서 앱으로 해당 입금액을 AI에 바로 배정한다. 앱은 사용자가 입력한 입금·배정 금액을 같은 시점에 기록하고, AI TWR은 배정 직후부터 계산한다. 실계좌 입출금 자동 감지와 별도 기록 화면은 초기에는 구현하지 않는다.
- **예상 문제:** 개인·전체 TWR을 계산하는 동안 앱이 모르는 실계좌 입출금이 발생하면 자금 이동을 투자손익으로 잘못 계산할 수 있다. 현재 사용 방식에서는 발생 가능성이 낮다고 판단해 우선 적용하지 않는다.
- **확인한 제약:** 2026-09-19 공개 [토스 REST v1.2.17](https://openapi.tossinvest.com/openapi-docs/latest/openapi.json)·[웹소켓 v1.2.2](https://openapi.tossinvest.com/openapi-docs/latest/asyncapi.json)에는 입출금 내역·발생 시각 조회나 입출금 이벤트가 확인되지 않았다. 매수 가능 금액은 입출금 내역이 아니며 주문·체결·결제 등으로도 달라질 수 있다.
- **후속 검토:** 실제 문제가 생기면 내부 예상 금액과 매수 가능 금액의 차이를 재확인한 뒤 사용자에게 입출금 여부를 묻고, 확인된 금액·통화·시각을 외부 자금 이동으로 기록하는 방식을 검토한다. 발생 빈도·수익률 오류 건수·확인 알림 오탐률을 보고 도입 여부를 판단한다.

### AI 손실 기준 자동 중지

- **현재 범위:** AI 설정은 운용금액만 사용하며, 손실률에 따른 자동 중지 기준은 두지 않는다. AI는 배정받은 자산만 사용한다.
- **관찰 지표:** AI별 TWR·현재 낙폭·최대 낙폭과 사용자의 수동 중지 시점을 기록한다. 초기 낙폭은 저장된 성과 평가 기록으로 계산하므로 기록 사이의 장중 저점은 포함하지 않는다.
- **후속 검토:** 실제 손실 수준과 수동 개입 사례를 확인한 뒤 최초 배정금 또는 성과 고점 대비 손실 기준으로 자동 중지할 필요가 있는지 검토한다. 도입 시 손실 제한 기준·미체결 주문 처리·재개 조건을 함께 정한다.

### AI 판단 실패 처리

- **상태:** 처리 방식을 아직 결정하지 않았으며 보류한다.
- **예상 실패:** AI 응답 시간 초과, 응답 형식 오류, 매수·매도·관망으로 해석할 수 없는 응답, 종목·가격·수량·판단 근거 누락, 필요한 시세·보유정보의 누락 또는 오래된 정보 사용이다.
- **추천 동작:** 불완전한 판단으로는 주문하지 않는다. AI 호출 자체의 일시적인 오류는 같은 판단 요청으로 한 번만 자동 재시도하고, 시세·보유정보 부족은 새 데이터를 확인하기 전까지 재시도하지 않는다.
- **재시도 실패 후:** 실패 사유를 기록하고 사용자에게 알린 뒤 해당 판단 주기만 종료한다. AI 전체를 자동 중지하지 않고, 다음 정기·조건 판단에서는 새 데이터로 다시 판단한다. 실패한 응답의 일부 내용이나 이전 판단은 재사용하지 않는다.
- **결정할 점:** 자동 재시도 여부·횟수, 사용자 알림 범위, 반복 실패 시 AI 중지 여부를 실제 전략과 운영 방식에 맞춰 정한다.
